## 1. Описание системы

Система представляет собой **программный комплекс** для:

- мониторинга **спортивных событий**,
- автоматического **расчёта вероятностей исходов**,
- отправки **уведомлений о выгодных ставках** («валуях») в **Telegram-бот**.

### 🛠 Стек технологий

| Слой | Технология |
|---|---|
| **Backend** | `Python`, `Django` |
| **Контейнеризация** | `Docker`, `Docker Compose` |
| **База данных** | `MySQL` / `PostgreSQL` (на базе данных `db`) |
| **Интеграция** | `aiogram` (**Telegram API**) |
| **Вычисления** | Собственный математический движок (**`MathEngine`**) на основе вероятностных моделей |

---

## 2. Порядок развёртывания и запуска

Для корректной работы системы используйте следующий алгоритм:

### 🔧 Подготовка окружения

- Убедитесь, что **Docker Desktop** запущен.
- Находясь в корневой папке `C:\betting_bot_project`, проверьте наличие файла **`.env`** с актуальными данными:
  - `TELEGRAM_BOT_TOKEN`,
  - `TELEGRAM_CHAT_ID`,
  - учётные данные БД.

### 🚀 Сборка и старт

```bash
# Команда для чистого запуска:
docker-compose up -d --build

# Команда для просмотра состояния:
docker-compose ps
```

### 🤖 Инициализация бота

> ⚠️ **Обязательно** отправьте команду `/start` вашему боту в Telegram от имени того аккаунта, чей ID указан в `TELEGRAM_CHAT_ID`.

## 3. Регламент работы и взаимодействия компонентов

Взаимодействие модулей происходит по следующему **циклу**:

| Этап | Компонент | Действие |
|---|---|---|
| 🔍 **Сбор данных** | Django ORM | Опрос базы данных `MatchOdds` на наличие записей с `notified=False` |
| 🧮 **Анализ** | `MathEngine` | Расчёт вероятности исхода и сравнение с текущими коэффициентами |
| 📤 **Уведомление** | Telegram Bot | Отправка сообщения в чат при выявлении «валуя» (**`value > 0.3`**) |
| ✅ **Фиксация** | Django ORM | Обновление записи в БД (**`notified=True`**) для предотвращения повторов |

## 4. Инструкция по устранению типичных ошибок

Если система **перестаёт реагировать**, следуйте этому порядку диагностики:

### ❌ Ошибка `chat not found`

- Проверьте, добавлен ли **бот в чат** и нажат ли **`/start`**.
- Убедитесь, что **`TELEGRAM_CHAT_ID`** в файле `.env` соответствует **ID пользователя или группы**.

### ❌ Ошибка `RuntimeError (Async context)`

- Убедитесь, что все обращения к БД обёрнуты в **`sync_to_async(list)(...)`** или **`sync_to_async(function())`**.

### ❌ Отсутствие реакции

- Проверьте логи командой:

```bash
docker-compose logs -f executor
```

- Убедитесь, что в БД есть записи с **`notified=False`**.
- Проверьте состояние контейнеров:

```bash
docker-compose ps
```

> 💡 Все контейнеры должны иметь статус **`Up`**.

## 6. Архитектура MathEngine: Ядро интеллектуальной аналитики

**Математический движок** является **ключевым компонентом**, отвечающим за **принятие решений**.

Его взаимодействие с системой организовано следующим образом:

| Аспект | Описание |
|---|---|
| 🧠 **Алгоритмическая база** | Использование **математического ожидания** и **вероятностных моделей** для оценки «валуйности» (**value**) коэффициентов |
| 📥 **Обработка данных** | Входные данные (команды, коэффициенты) проходят через модель, которая возвращает **прогнозную вероятность** исхода |
| 🎯 **Логика принятия решений** | Приложение рассчитывает **коэффициент валуйности** через метод **`calculate_value`**. При превышении порога в **`0.3`** система автоматически переходит к формированию уведомления для **Telegram-бота** |
| 🔗 **Интеграция с Django** | Движок работает как **независимый синхронный сервис**, что обеспечивает **высокую скорость вычислений** при обработке потока матчей |

## 7. План тестирования системы

Перед запуском **«в бою»** необходимо проверить **каждый компонент отдельно**, чтобы исключить **скрытые сбои**.

### 🧪 Модульное тестирование (Unit Tests)

- Напишите тесты для **`MathEngine.calculate_value`**, подавая на вход **заведомо известные коэффициенты**, чтобы убедиться в **корректности математики**.
- Проверьте работу **`MathEngine.get_match_prediction`** на корректность обработки **имён команд** (например, при наличии пробелов или спецсимволов).

### 🔗 Интеграционное тестирование

- Создайте **тестовую запись** в базе данных с **`notified=False`** и **вручную запустите цикл обработки**, чтобы проследить **весь путь**: от базы до **уведомления в Telegram**.
- Проверьте, **меняется ли статус `notified` на `True`** в базе данных **сразу после отправки сообщения**.

### ⚡ Нагрузочное тестирование

- Попробуйте добавить в базу **50–100 тестовых записей одновременно**, чтобы убедиться, что `executor` корректно обрабатывает их **в цикле**, **не «зависая»** и **не создавая дубликатов** уведомлений.

## 8. Оптимизация взаимодействия модулей

Чтобы система работала **стабильно** при **росте данных**:

| Направление | Что делать |
|---|---|
| 🔄 **Асинхронная очередь задач** | Если количество матчей будет расти, `while True` с `asyncio.sleep(60)` может стать **узким местом**. Рекомендуется внедрить **Celery** или **встроенную очередь Django** для выноса отправки уведомлений в **фоновый процесс** |
| 📝 **Логирование** | Настройте логирование так, чтобы ошибки **базы данных** и ошибки **API Telegram** писались в **разные файлы или потоки**. Это поможет **быстрее находить причину простоя** системы |
| 🔐 **Изоляция конфигурации** | Убедитесь, что все **чувствительные данные** (токены, пароли) хранятся **исключительно в `.env`**, а не зашиты в код |

## 9. План расширения проекта

Для подготовки проекта к **профессиональному уровню** (например, для **Сколково**) стоит рассмотреть следующие шаги:

### ⚙️ Добавление системы логики (Rules Engine)

- Внедрите **конфигуратор правил**, чтобы можно было **гибко менять порог «валуйности»** (например, от `0.3` до `0.5`) **через настройки**, не меняя код самого бота.

### 📊 Расширение аналитики

- Добавьте **модуль сбора статистики**: сохранение **всех отправленных уведомлений** и последующий анализ того, **сколько из них «сыграли»** (процент точности предсказаний).

### 🖥 Интерфейс администратора

- Используйте **встроенную панель администратора Django** для:
  - ручного управления матчами,
  - просмотра статуса уведомлений,
  - добавления новых команд / лиг **вручную**.

### 🗄 Масштабируемость БД

- Если текущая база данных **перестанет справляться** с объёмом, рассмотрите **переход на PostgreSQL** с использованием **индексов по полю `notified`**, чтобы поиск записей проходил **практически мгновенно**.
